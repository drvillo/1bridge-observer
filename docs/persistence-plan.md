# Durable observer store increment plan

> This is a reviewed-before-code increment under the Superpowers test-driven workflow. It builds storage only. Until a source puller and authority replay invoke it, the observer makes no coverage claim.

**Store status (2026-10-14):** Root `schema.sql` defines the initial nine observer-owned tables, foreign keys/checks/indexes, a version-1 marker, collision guard and structural catalog fingerprint. `installObserverSchema` executes the exact file on one `pg` client inside a caller-owned transaction after transaction-local SHA-256 digest setup; the SQL's advisory lock serializes installers. `registerObserverFeed` checks the independently pinned signed anchor, retains exact bytes and creates one cursor in the same transaction. `claimObserverLease` uses an atomic database-time update and advances a fencing epoch even when the same worker reclaims. `beginObserverTarget` fixes exact provisional bytes under a fenced claim, and `stageObserverBatch` retains bounded exact bytes, cursor continuity and repeat-page idempotence without advancing accepted coverage. `acceptObserverTarget` replays a complete retained prefix under the independent pin outside the commit transaction, then checks the fenced cursor again and commits accepted bytes/head atomically. `quarantineObserverTarget` can preserve a complete replay-rejected attempt and unresolved finding without replacing accepted coverage; a later corrected attempt with the same signed head succeeds in the integration test. Real-driver checks cover these paths in disposable Postgres and local Supabase Postgres 17.6. The schema fingerprint detects accidental drift but is not a security seal against a database administrator; a PostgreSQL major-version upgrade may need an explicit migration if catalog rendering changes. A bounded source poll core is implemented and tested against fixture HTTP. It retains deduplicated source-nonconformance diagnostics separately from cryptographic replay findings; signed coverage and a production invocation route remain unimplemented. No live independent coverage is claimed.

The initial DDL uses one database identity sequence for target attempt IDs; `(feed_id, attempt_id)` is the composite row identity. The planned store must not assume the numeric sequence restarts for each feed.

**Goal:** Retain exact pulled evidence, a resumable cursor, leases and unresolved findings in customer-owned Postgres with crash-safe, competing-worker behavior. The same SQL must work against ordinary Postgres and a customer Supabase Postgres connection.

## Ground truth

- The repository has the Next.js bootstrap and liveness route, source client, fixed-target replay, reviewed SQL DDL and a `pg` store (`src/lib/store.ts`). Schema installation, exact pinned feed registration, fenced leases, provisional target fixation, unverified staging, verified target acceptance and replay-rejected findings are implemented. A bounded poll core exists; its production invocation route and signed audit statement remain absent.
- `docs/architecture.md` requires a customer-controlled Postgres cursor, immutable leaves/checkpoints, durable gaps/findings, short transactions and no provider service-role credential. The authority library's action/replay state serialization is not finalized; this increment must not pretend to verify leaf bytes.
- [node-postgres transaction guidance](https://node-postgres.com/features/transactions) requires one client for all statements in a transaction; the pool's separate query calls cannot form one atomic commit. `DATABASE_URL` is already parsed by `loadObserverConfig` but is not used by a route.
- Local Docker is available. A dedicated ordinary Postgres test container and a separate temporary schema/database in local Supabase can verify compatibility without touching app-owned tables. Credentials must never appear in test output or committed files.

## Journey and states

| Step | Caller | Durable state before → after | Failure |
|---|---|---|---|
| Install schema | Customer setup/CI | Empty DB → idempotent observer-owned tables and version marker | Unsupported older/newer schema refuses startup; app tables unaffected |
| Register feed | Authorized local setup | Out-of-band anchor pin, exact signed anchor bytes and source URL → one immutable feed identity row | Pin mismatch, conflicting feed identity or unsupported key never silently overwrites |
| Claim work | Cron/manual worker | Free/expired lease → owned bounded lease at database time | Competitor receives no lease; stale owner cannot commit |
| Fix target | Lease owner after discovery | No active target or same target → immutable **provisional** target checkpoint bytes/hash/size under lease and cursor CAS | Other active target, stale lease or malformed checkpoint rejects; full cryptographic authentication follows historical replay |
| Stage exact batch | Future poll core | Expected staging cursor/version/target plus exact fetched leaves/checkpoints → one transaction advancing only the staging cursor | Wrong start/target/version/lease, changed duplicate leaf, partial write or crash rolls back |
| Accept sealed checkpoint | Future poll core | Staged contiguous evidence plus successful library replay through the signed checkpoint → one transaction advancing accepted size/head | Failed replay, stale lease or crash leaves accepted coverage unchanged |
| Finish or quarantine target | Future poll core | Accepted fixed target → clear active target; rejected target → retain exact fetched evidence/finding and clear active staging cursor for a different candidate | Cannot discard accepted evidence, hide rejection or reset the accepted head |
| Record finding | Future poll core | New evidence/gap → append-only unresolved finding | A later unrelated success cannot delete it |
| Resume | New worker | Staged cursor/target/evidence and separately accepted checkpoint → replay retained evidence, then fetch next bounded batch | No repeated acceptance or skipped index |

These are persistence outcomes, not evidence-verification outcomes. Staged bytes are not verified coverage. A caller may label a checkpoint accepted only after authority-library replay; storage alone must never issue a signed coverage statement.

## SQL and API contract

Keep one `schema.sql` at repository root for the initial migration, avoiding a speculative directory convention. It creates an observer-specific version table and prefixed tables under the selected connection's current schema, without requiring `CREATE SCHEMA` privilege. Use parameterized SQL; quote no user-provided identifiers. For tests, select an isolated database or schema through the connection setup, not interpolated SQL. Reject wrong schema version rather than silently evolving a deployed database.

`observer_feeds` has immutable `feed_id` (64 lowercase hex), `anchor_pin` (64 lowercase hex), exact canonical signed-anchor bytes, `source_base_url`, and creation time. Feed registration parses and verifies those bytes through the published authority library against the separately configured expected pin; the pinned anchor supplies the initial provider checkpoint SPKI/key ID. The anchor may be obtained from the source, but the expected pin must come from independently authenticated customer configuration. `observer_cursors` has one feed row with separate `staged_next_index` and `accepted_size` (nonnegative bigint **bounded to JS MAX_SAFE_INTEGER**), accepted checkpoint hash, active provisional target attempt ID/hash, staged checkpoint tail hash/position, version bigint and monotonically incrementing lease epoch, lease owner and database-time expiry. A target checkpoint signed by a rotated provider key cannot be authenticated at discovery; target fixation and staged bytes do not label it accepted. `observer_leaves` and `observer_checkpoints` retain **accepted** exact canonical bytes under immutable feed/index or feed/hash keys. Attempt-scoped `observer_staged_leaves` and `observer_staged_checkpoints` retain unaccepted bytes under `(feed_id,attempt_id,index)` and `(feed_id,attempt_id,position)`; a staged checkpoint also has a unique hash within that target, size and predecessor. A leaf hash uses the RFC 9162 domain-separated `hashLeaf(leaf_bytes)` from the authority library (SHA-256 of `0x00 || leaf_bytes`, **not** raw SHA-256 of the bytes). Accepted or staged bytes are never silently replaced. `observer_findings` retains type, canonical evidence bytes, first/last seen timestamps and unresolved status; only a later explicitly verified resolution transaction may mark resolved. No free-form JSONB claim is treated as authenticated evidence. Add foreign keys and length/check constraints, and indexes for range reads and unresolved findings. Keep sensitive proof bodies out of SQL logs. Convert `pg` bigint strings to JS numbers only after explicit nonnegative/safe-integer validation; reject oversized DB values.

`openObserverStore(connectionString)` owns one `pg.Pool` and a clean close method. `installObserverSchema(store)` uses one acquired client and **one transaction** for all DDL plus the version marker, serialized by a fixed observer-specific transaction advisory lock. On first install it refuses any colliding `observer_*` object, then creates the exact tables. On repeat it checks version 1, the recorded schema-file digest and required catalog columns/constraints/indexes; `CREATE TABLE IF NOT EXISTS` alone is insufficient. Crash/rollback leaves no partial installed schema. `registerObserverFeed(store,config)` inserts one independently pinned **verified signed anchor** or checks byte-for-byte agreement on retry; no overwrite. This increment adds the user-requested first-party `@drvillo/1bridge-authority` library as an immutable commit-pinned dependency once its lifecycle API is independently reviewed, built and published; a cross-repo signed-anchor fixture must pass before registration is enabled. The config phase adds `ANCHOR_PIN` (customer-checked 64 lowercase hex) and `SIGNED_ANCHOR` (canonical base64url encoded signed-anchor bytes); the latter may come from the source but is accepted only against the former. `CHECKPOINT_PUBLIC_KEY` from bootstrap was removed in the anchor-config increment, so the verified anchor is its sole initial provider-key source. `claimObserverLease(store,feedId,workerId,duration)` uses database time and a conditional update that increments a per-feed `lease_epoch` on **every** claim, including same-worker reclaim; it returns an opaque claim containing that epoch, expected cursor version and database expiry. `beginObserverTarget(store,claim,checkpoint)` fixes a structurally valid **provisional** target hash, size and exact signed bytes under the valid lease/version; it refuses a different active target. Each immutable target-attempt row has a database-generated `attempt_id`, the exact target hash/head bytes and `active`, `accepted` or `quarantined` status. A quarantined hash may be retried under a new attempt ID; old conflicting bytes remain retained. Historical checkpoint-key authentication is a later replay obligation, not a precondition to storing the tentative fetch target or a store guarantee; the bounded poll core is implemented, but no production invocation or coverage statement is shipped. `stageObserverBatch(store,claim,batch)` uses **one acquired client and one transaction**: lock cursor, check owner, lease epoch, `lease_until > clock_timestamp()`, version, target hash/size and start, verify every index contiguous, insert exact leaves/checkpoints, compare any existing row bytes on retry, advance only the staging cursor/checkpoint tail/version and commit. Every successful `beginObserverTarget` or `stageObserverBatch` returns a refreshed claim carrying the new cursor version; the old claim is stale even under the same lease. `acceptObserverTarget` reads the retained full prefix, verifies it with the authority library outside the transaction, and advances `accepted_size` and the accepted head only if the fenced cursor and fixed target still match at commit. A checkpoint spanning multiple source pages remains unaccepted between those pages. An exact redelivery of a fully staged prior batch under a current claim returns `alreadyApplied` after byte-for-byte row/target comparison, without advancing cursor/version; partial overlap or changed bytes reject. `quarantineObserverTarget` retains a replay-rejected attempt and appends an unresolved finding without overwriting prior evidence. Reads return defensive copies/primitive values. A connection failure or serialization/deadlock conflict is reported for bounded retry by the caller, never interpreted as tampering.

The authority library's `HistoryFrontier` and authority replay state will be reconstructed from retained immutable leaves until a later versioned snapshot format is specified. This avoids inventing unsafe JSON serialization of an opaque trusted state. It is O(N) on cold restart; benchmark before claiming large-feed scalability. The staging cursor cannot certify a prefix merely because rows exist; `acceptObserverTarget` performs exact replay before it commits. The public status page and `/api/health` remain liveness-only.

The first staged checkpoint must immediately follow the accepted checkpoint hash, or be the signed size-zero genesis when none has been accepted. Every later staged checkpoint must have `previous` equal to the staged tail's statement hash; its position increments by one. The store checks these structural links and exact duplicate bytes, while the poller verifies signatures, authority state and roots. A two-page pull under one lease passes the refreshed claim from page one to page two; a stale pre-page version token fails. A crash resumes from the durable staged leaf index and staged checkpoint tail after replaying the stored candidate.

When the fixed target is cryptographically accepted, `acceptObserverTarget` atomically copies the verified attempt-scoped evidence into accepted immutable rows, advances accepted size/head, marks that target attempt accepted and clears the active target/staging cursor. When replay proves the candidate invalid, `quarantineObserverTarget` atomically records the finding, marks the target and its exact staged evidence quarantined, clears the active pointer and resets staging cursors to the last accepted size/head. It never deletes or overwrites the rejected evidence. A source timeout or temporarily missing page leaves the target active and coverage pending; availability alone is not a cryptographic finding. The next candidate, including the same signed target hash with corrected source bytes, may start under a new attempt ID only after accept or quarantine, so a bad provisional response cannot permanently wedge the feed. A competing valid fork from an already accepted head is retained as a finding, not silently selected.

Cold restart reconstructs cryptographic state from accepted and staged exact evidence. The currently published complete-prefix API rejects more than 10,000 leaves or 32 MiB. A bounded-page in-process library session is planned, but even that requires replay from genesis on every cold Vercel invocation until a trusted durable continuation is designed. The store must report coverage pending if replay exceeds an invocation budget; it must not claim unbounded Hobby catch-up. Benchmark representative 100/1,000/10,000-leaf feeds and document the supported operating envelope before deployment. A customer may run the same observer continuously outside Vercel for larger feeds; this is an operational option, not a substitute for cryptographic checks.

| `stageObserverBatch` | Atomic exact evidence/staging cursors update and refreshed version token | Keep; no coverage claim |
| `acceptObserverTarget` | Replay retained prefix and commit the still-current target | Implemented; no caller-supplied verification claim |
| `quarantineObserverTarget` | Preserve replay-rejected candidate/finding and free the active target | Implemented; incomplete or valid targets cannot be quarantined |
| `recordObserverFinding` | Deduplicate and retain source-nonconformance diagnostics under a fenced lease | Implemented; no automatic clearing |

## Test-first plan

1. Add a real-Postgres integration test importing the missing store API; observe red. Add `test:integration` and exclude `*.integration.test.ts` from default `pnpm test`. Run an isolated ordinary Postgres container/database, plus a separate local Supabase test database/schema created and removed by the harness; never touch app-owned tables. Install schema twice, including simultaneous installers, and compare table/version/catalog state; wrong version, same-version mutated shape, object collision and failure between DDL/marker all fail without partial state. Implement smallest SQL/store module.
2. Test immutable feed registration from an independently pinned signed anchor, substitute provider key/anchor supplied by the source, conflicting anchor/source and malformed feed/index/hash; test no secret leak. Deliberately remove one check and observe the targeted failure.
3. Test competing leases using two pools/clients, expiry with database time, stale claimant commit, **same worker ID reclaim with old epoch**, interrupted transaction rollback, target fixation/staging, two consecutive pages using refreshed version tokens, stale old-token rejection, redelivery of the same batch, changed same-index bytes, duplicate checkpoint hash with changed bytes, missing/wrong staged checkpoint predecessor, noncontiguous leaf batch, bigint overflow and concurrent target/cursor CAS. A staged page must leave accepted size/head unchanged, including when one checkpoint spans several pages. Assert the domain cursor/evidence rows, not query mocks. Use fault injection at the transaction boundary.
4. Test accepted-target completion clears the active target; a canonical wrong leaf for a valid signed target is quarantined with exact retained evidence, then the same signed target hash with correct bytes succeeds under a new attempt ID; and a transient unavailable page leaves the target pending. Findings survive restarts and unrelated successful batches; no success route or report is added. Verify compatibility against ordinary Postgres and isolated local Supabase Postgres where available. Record exact versions and any unrun target.
5. Run `pnpm test`, `pnpm test:integration`, `pnpm lint`, `pnpm typecheck`, `pnpm build`, `git diff --check`, a compiled store import smoke and independent spec/quality review. Existing bootstrap route behavior remains unchanged. Later source verification must add a cross-repo fixture and may change the storage contract via an explicit migration.

## Principles, smells and verification

SRP: store owns durable facts and concurrency, authority library owns cryptography, future poll core owns fetch/verification. DRY: one SQL schema and one commit path. KISS: short Postgres transactions/CAS, not queues as evidence retention; no ORM or migration framework. YAGNI: no replay-state serializer or signed statement until a verified feed exists. Boy Scout cleanup is limited to touched files and separate from behavior changes. The first-party authority library is pinned to an immutable revision; `pg` is the observer's sole new third-party runtime dependency, used for the user's requested ordinary Postgres/Supabase support. No 1bridge app source or dependency changes occur in this increment.
