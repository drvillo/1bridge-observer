# Versioned pull source contract

Status: proposed cross-repository wire contract for the fixture publisher, observer and later 1bridge app adapter. No route in either repository currently serves this contract. The customer-run observer is a **puller**; a source route never calls it. Strict audit policy never makes a release wait for observer availability.

## Authentication and independent trust

The observer operator independently obtains the signed customer anchor and its expected 64-hex pin. The anchor pins feed/workspace and the initial provider checkpoint key. The source may return a copy, but cannot replace the operator's pin. A customer-scoped `SOURCE_READ_TOKEN` sent as an `Authorization: Bearer` header is the **proposed** private-feed authorization mechanism, pending the user's explicit decision because it adds a new app-issued machine credential convention. If selected, that operational credential is distinct from the observer's inbound `CRON_SECRET`, database URL, any app Supabase service-role key, and user blind proof-access tokens. It grants no write action and is not itself a cryptographic trust anchor. A customer can run multiple independent observer deployments with separate read credentials.

Full canonical authority revisions reveal pseudonymous subject/scope hashes, public P-256 keys, action class labels and the policy body. The source therefore requires a configured observer/auditor read capability; no implementation may claim the full feed is metadata-free or universally public. The app must restrict audit-policy bodies to a non-sensitive schema. Encrypted audience evidence openings travel through separate authorized proof reads, not the general feed. Anyone can deploy the open-source observer, but only a customer-authorized observer can read a protected feed.

## Proposed HTTPS routes

The app and fixture publisher implement the same `v1` GET protocol under a feed ID. These are **proposed names**, not current app endpoints:

| Request | Response | Acceptance rule |
|---|---|---|
| `GET /api/governance/v1/feeds/{feedId}/head` | `{version:1,signedAnchor:string,signedCheckpoint:string,checkpointHash:Hash}` | Verify the independent anchor pin/signatures; structurally parse and hash the **provisional** target checkpoint, then authenticate its provider signature only after replaying the intervening chain and any customer-authorized key rotation. Never trust `latest` as a global-freshness fact |
| `GET /api/governance/v1/feeds/{feedId}/checkpoints?after={hash-or-start}&target={hash}&limit={1..16}` | `{version:1,target:Hash,after:'start'\|Hash,items:string[]}` with ordered canonical base64url signed checkpoints | `after=start` begins with signed size-zero genesis; otherwise first item immediately follows `after`; each later `previous` equals the prior statement hash; no skip or alternate target |
| `GET /api/governance/v1/feeds/{feedId}/leaves?start={index}&target={hash}&limit={1..64}` | `{version:1,target:Hash,start:number,items:string[]}` with contiguous canonical base64url leaf bytes | Assign each leaf its position from requested `start + item offset`; authenticate that order through the recomputed target history root/size and receipt indices. No empty nonterminal page |

Each response is the authority library's **canonical JSON byte encoding** of an exact plain object with precisely the named fields and types above; `Hash` is 64 lowercase hex characters, `start` is a nonnegative safe integer, `items` is a dense array no longer than the requested `limit`, and every item is canonical unpadded base64url. Parse the whole envelope with `parseCanonical`, which rejects duplicate JSON keys and noncanonical numbers/order, then reject extra/missing fields, oversized arrays and noncanonical inner bytes. The observer streams and bounds the **decoded `Response.body` bytes** before parsing to 64 KiB for head/checkpoints and 256 KiB for leaves; native fetch can decompress HTTP content encoding before exposing those bytes. This does not bound on-wire transfer size. It also bounds the sum of decoded checkpoint bytes to 64 KiB and leaf bytes to 256 KiB. Decode signed material with `parseCanonical`; compare the exact re-encoded bytes with the original. No unsigned response field authenticates evidence. The source's echoed target and start/after are untrusted assertions checked against the pinned target and requested cursor. A fixed target remains addressable while newer heads appear.

`items` must contain at least one entry if `after` is before `target` in the checkpoint chain or `start` is below the target checkpoint's size. The only valid empty checkpoint page has `after=target`; the only valid empty leaf page has `start=target.size`. The final nonempty checkpoint item must equal `target` when checkpoint paging is complete; the final leaf index must be `target.size-1` when leaf paging is complete. The client never infers completion from a short page, a source-provided `hasMore` flag or an HTTP connection close. A response with an unavailable target/item (404/409), denied read (401/403), throttling (429), network failure or 5xx leaves coverage pending and schedules a bounded retry; it is not, by itself, proof of suppression. Malformed 200 responses are recorded as source nonconformance and remain unaccepted. A conflicting authenticated signed checkpoint, fork or independently held receipt is retained as cryptographic evidence, never collapsed into an ordinary availability error.

The signed genesis checkpoint has size zero, RFC empty history root, initial authority root/policy epoch and `previous:null`; it uses the provider key from the pinned anchor. Every later signed checkpoint has `previous` equal to the hash of the immediately preceding checkpoint *statement*. The observer pulls all intervening checkpoints after downtime, even when a direct old→new RFC consistency proof would validate the history root. The head response is only a provisional fixed target: a signed checkpoint from a rotated provider key cannot be authenticated from the initial pin until its intervening root-signed rotation leaf is replayed. Storing that target or its hash is not acceptance. Between consecutive checkpoints, the observer retrieves and replays every newly covered authority and completion leaf, reconstructs history root/size and authority root/policy, verifies the customer-authorized provider key at that point, the signed predecessor and RFC consistency. Because it retains all contiguous leaves, it derives RFC consistency proofs locally rather than trusting a source-provided proof field. A future signed-key rotation is authorized only by an intervening customer-root-signed authority leaf. For each completion leaf, replay checks the actor signature and active historical binding, unique operation ID, actor-key stream predecessor, authenticated `observedCheckpointHash` ancestry, and the prior receipt's inclusion and historical checkpoint authorization against the same chain. The library's standalone actor-signature and receipt-inclusion functions do not themselves establish these combined properties. A partially fetched target is never called accepted.

## Backlog and persistence

One poll claims a bounded lease, fixes a provisional signed target and fetches outside database transactions. Exact contiguous bytes advance a **staging** cursor under an expected version/lease epoch; only successful library replay through a sealed checkpoint advances the separate **accepted** cursor/head. A target rejected by replay is quarantined with its evidence so the next candidate can be tried; an unavailable source leaves coverage pending. Daily Vercel Hobby cron can restart work; manual invocations and optional queue wake-ups can accelerate catch-up. Failed or duplicate invocations cannot skip a range or clear a durable finding. The source must retain canonical leaves and checkpoint chains for the customer's configured audit-retention period; if an older item is unavailable, the observer reports incomplete coverage and cannot certify the target. Ordinary Postgres and customer Supabase are supported by the same observer SQL schema.

An independently retained client receipt or later signed action **under the same actor signing key** with an embedded prior receipt can expose a withheld predecessor. A new action under another actor key does not expose that key's suppressed tail. Reconciliation checks exact operation/action/leaf identities against contiguous pulled history and retains unresolved gaps. A source-only poll cannot discover an isolated decision withheld from every response and every external custodian. An unanswered request alone is not proof of malicious suppression. Receipt archive transport and its independent authorization are a separate pending decision; the app never pushes to the observer.

## Test and deployment gate

Before app source edits, an in-repo fixture publisher and real observer must pass tests for empty genesis, authority bind/revoke/provider-key rotation, two actor actions/receipts, paged checkpoint and leaf backlog, old signed head, validly signed wrong authority root/policy, skipped/changed leaf, forked prior receipt, source outage/retry and independent receipt conflict. Real Postgres and isolated Supabase-compatible persistence, Next production build and local HTTP pull smoke must pass. A Vercel deployment guide must explain Hobby cron cadence and how to configure `SOURCE_READ_TOKEN`, `ANCHOR_PIN`, `SIGNED_ANCHOR`, `DATABASE_URL`, `CRON_SECRET` and observer signing-key custody. A deployed Vercel smoke is reported only if actually run.
