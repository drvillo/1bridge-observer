# Independent observer architecture and implementation order

Status: design contract and partial implementation, 2026-10-14. The observer has a runnable Next.js app, bounded source pull and process-local replay, a Postgres store for staged/accepted evidence and signed prefix reports, and a protected bounded poll route scheduled daily by Vercel. A store API retains externally supplied canonical receipts and signed reports bind the exact known set plus pending or unmatched statuses. External authenticated receipt ingress, deployed custody and a production observer are still absent. The user selected a public, customer-run, TypeScript observer that pulls 1bridge, supports Vercel and ordinary Postgres/Supabase, and never participates in a release decision. This design uses the 1bridge D1–D4 shared architecture.

## Ground truth and trust boundary

- The public authority library implements RFC 9162 roots/proofs and a history frontier, canonical encoding, P-256 signatures, an ordered map, audience commitments, signed checkpoints, actions, receipts and mixed-history replay (`../1bridge-authority` is a sibling checkout; see its `src/index.ts`). The observer imports its pinned exports rather than inventing parallel cryptography.
- The provider app currently has no governance pull endpoint or authority journal (`ubo-guard/.planning/research/1bridge-verifiable-governance-design-review.md` is a design lead, not deployed evidence). Fixture endpoints can exercise the observer before app integration.
- [Vercel Hobby cron](https://vercel.com/docs/cron-jobs/usage-and-pricing) permits a daily schedule with hour-level timing; [Functions](https://vercel.com/docs/functions/limitations) have bounded execution. [Vercel Queues](https://vercel.com/docs/queues) are available on all plans in beta, but queue messages are wake-ups rather than independent evidence retention.
- The observer operator independently pins the feed identity, customer root and authorized provider checkpoint key. A key supplied solely by the source cannot authenticate the source. The operator controls its own signing key, Postgres credentials and Vercel project. It never receives the provider Supabase service-role key.

## Journey and states

| Step | Caller | Before → after | Failure behavior |
|---|---|---|---|
| Configure | Customer operator | Independently verified pins and source URL → local feed config | Invalid or changed trust anchor rejects; source cannot silently replace it |
| Discover | Daily cron or authorized manual trigger | Durable old head → fixed signed target head | Timeout/outage records availability state; no false fork accusation |
| Pull | Worker | Cursor below target → bounded contiguous canonical leaf batch | Missing index, duplicate, wrong bytes or size leaves durable unresolved range |
| Verify | Worker with authority library | Supplied batch → checked history/authority/action state | Invalid signature, transition, map root or proof records finding, stops advancement |
| Commit | Worker and own Postgres | Verified batch and cursor → one durable transaction | Redelivery/competing workers compare prior cursor/head; no skipped batch |
| Report | Observer signer | Exact verified head/coverage and unresolved findings → signed statement | A partial batch never produces full-head coverage |

An observer outage does not change 1bridge's normal or Enterprise/Government strict-auditing release behavior. Strict mode strengthens configured checks, durable findings and signed reporting without witness-before-release.

## Deployment and data ownership

Use TypeScript and a Node runtime compatible with the current 1bridge Next.js/Vercel ecosystem. The legacy single-feed `GET /api/poll` is protected by a customer-held `CRON_SECRET`; it uses a 20-second work budget, 16 leaf pages and 16 checkpoint pages. The shared deployment instead uses the protected daily/manual `GET /api/shared-poll` and a private Vercel Queues consumer. A successful poll can enqueue another bounded scan when it made durable progress or has unselected catalog batches, capped at 128 follow-up calls per seed. Each queued delivery rereads Postgres and uses the same fenced poll/report path; the queue contains only scheduling counters. A lost/expired message cannot erase the durable cursor or findings, and the next cron/manual call resumes. Queue send failure does not invalidate a successfully signed report. Both routes have local build and real-Postgres contract tests, but no deployed Vercel queue/cron smoke yet.

The customer's Postgres owns configured feeds/pins, accepted checkpoints, exact processed leaf hashes and replay state, cursors/lease tokens, unresolved gaps/conflicts, and signed coverage statements. The v3 schema adds immutable, feed-scoped receipt bytes, bounded to 10,000 receipts and 16 MiB per feed; the installer verifies v1/v2 catalog state before migration and v3 state on repeat. Earlier migrations are frozen. The combined unresolved set supports up to 20,000 hashes from at most 10,000 archived receipts and 10,000 source findings. A report is signed only after the accepted prefix is replayed from retained bytes under the independent anchor pin. It binds the accepted checkpoint and unresolved finding set to one report revision, which advances on acceptance, new findings and first retention of a known receipt but not staging or identical receipt retries; a changed report revision invalidates an in-flight insertion, and a retry can recover after acceptance/signing crashes. The read API verifies each stored report under the separately configured anchor pin and observer public key, but returns the highest stored revision, which can temporarily lag an accepted cursor during crash recovery. Consumers apply their own signed-checkpoint freshness policy. Finding resolution is not yet implemented and direct SQL edits are unsupported because they bypass revision tracking. The schema must work unchanged with ordinary Postgres or a customer Supabase Postgres URL. Keep migrations in this repository. Use parameterized SQL and a single client for each transaction; no DB transaction spans a network call. Lease expiry controls duplicate work, while head/cursor compare-and-swap controls correctness under competing invocations.

The source read API will expose one fixed target signed checkpoint, every intervening signed checkpoint since the observer's retained head, contiguous ranges addressed by exact start/limit/target size or ID, and the historical authority material needed to replay each event. The authority library's checkpoint `previous` refers to the immediately preceding signed statement, so jumping directly from an old head to a latest head is insufficient after missed publications. Route names and JSON envelopes will be fixed in a shared contract before implementation. The observer validates response bytes rather than trusting pagination metadata. It cannot assert that a source response is globally latest merely because it is well signed.

## Detection and limits

A signed receipt retained outside provider control names a completed event/index/head. If a later pulled feed omits it, the observer retains an unresolved gap or a cryptographic conflict once contradictory signed material is available. An unanswered request is an availability failure, not proof of tampering. Signed incompatible heads prove equivocation to a verifier that receives both. A source-only pull cannot detect an entirely hidden, coherent branch without independent evidence of it. Client-originated asynchronous receipt copying remains the recommended independent channel. Programmatic receipt retention and report reconciliation are implemented, but transport authentication and client copying remain undecided. The provider never pushes events to this observer.

The HTTP adversarial test `test/verify-source.test.ts` now publishes a fully re-signed branch that omits one action, then publishes a later actor-signed action citing the omitted action's receipt. Fixed-target polling rejects that branch as a missing first action. A control branch with the same omission but no citation verifies successfully. This demonstrates eventual detection **when a later signed publication carries the predecessor evidence**; it does not make a wholly withheld coherent branch detectable by source-only polling.

## Implementation phases and tests

1. Finish the authority library's checkpoint, action/authority replay and receipt verification contracts. Freeze shared fixture vectors and import the tested package. No app source edit occurs here.
2. Implement a deterministic source fixture and pure bounded pull/verify state machine. Test outage, malformed payload, rollback, fork, missing index, wrong authority transition, partial progress, and honest no-op polling with failing tests first.
3. Implement customer-owned Postgres migrations/repository and test real transactions, crash points, concurrent workers, replay and retained findings on both ordinary Postgres and a Supabase-compatible connection path.
4. Add Vercel/Node invocation, daily cron setup, bounded continuation and manual operation. The protected poll route, private shared queue consumer, separate read-only report routes, observer-owned signing key configuration and prefix reports have local tests; a deployed preview smoke remains.
5. Add authenticated independent receipt ingress and client copying once the transport is settled; test an offline backlog and a known withheld tail, including the negative case where no independent copy exists. Run cross-repo fixtures before touching 1bridge application source.

The Next.js app, source verifier, `pg` store and bounded poll route have local package and disposable Postgres integration checks. The route can resume a partial target, accept fully replayed evidence, quarantine invalid evidence and retain a signed prefix report that states the exact known receipt set, or `none` when no receipts have been supplied. The comparator and archive are tested against disposable Postgres with pending-to-matched evolution, wrong-feed rejection, exact-byte idempotence and mutable inputs. On 2026-10-15, the full 30-test integration suite passed on both disposable Postgres 17 and a disposable database inside local Supabase Postgres 17.6; the opt-in running-1Bridge source test was skipped in both runs. Both wrappers now load one schema fixture so the Supabase run covers newly added shared-observer tests. No deployed Vercel smoke or production 1bridge feed is claimed.
