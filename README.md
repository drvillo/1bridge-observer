# 1bridge independent observer

Public, customer-operated pull observer for 1bridge governance evidence. This repository has a bounded pull client, process-local fixed-target verification, a test-only HTTP governance source, a durable Postgres store, and a bounded poll route that resumes staged evidence after an outage. A malformed source response creates a durable nonconformance finding; an outage does not create a cryptographic accusation. The observer signs reports for its verified prefix and unresolved findings. Its store can compare a supplied batch of receipts with retained accepted evidence, but it does not yet archive external receipts or include their reconciliation in signed reports. A running health endpoint is not an audit assurance.

## Run locally

Use Node.js compatible with Next.js 16 and pnpm 10.29.3. Run `pnpm install --frozen-lockfile`, then `pnpm dev` for the local app or `pnpm build && pnpm start` for a production build. `GET /api/health` returns `{ "status": "up" }` to indicate process liveness. The static home page states the current scope.

Copy `.env.example` to a private environment file and supply customer-controlled values. The configuration loader in `src/lib/config.ts` validates the runtime settings; the home page and health route do not read them. `src/lib/source.ts` fetches a provisional head and exact checkpoint/leaf pages; `src/lib/verify-source.ts` replays one fixed target under the independent anchor pin in a single process and refuses incomplete budgets. Tests exercise this path against a local HTTP governance publisher. `src/lib/store.ts` uses `pg` to install or upgrade `schema.sql` and `schema-v2.sql` inside one transaction, register exact independently pinned feed bytes, claim fenced database-time leases, fix one exact provisional target, and stage contiguous source bytes with an idempotent cursor. Staging advances no accepted coverage. `acceptObserverTarget` replays retained bytes under the independent pin before committing accepted rows; `quarantineObserverTarget` retains a complete rejected attempt and unresolved finding so corrected source bytes can be retried. `src/lib/poll.ts` bounds HTTP pages and elapsed time, resumes an active target after outage, and invokes acceptance or quarantine. The replay path is bounded to 10,000 leaves and 32 MiB. `openObserverStore(DATABASE_URL, schemaName)` requires the named schema to exist; it defaults to `public` in a dedicated observer database. The protected `GET /api/poll` route installs/checks the tables, claims a fenced lease, performs up to 16 leaf pages and 16 checkpoint pages within a 20-second work budget, releases the lease, then replays retained accepted evidence and stores a signed coverage report. After a crash between acceptance and signing, the next authorized poll can create the missing report. The provider has no production governance feed yet, so no live independent coverage is claimed.

## Deploy on Vercel

Create a separate Vercel project from this public repository. Provision customer-controlled Postgres, either as a dedicated database or as a dedicated schema in a shared project. For a shared database, create the schema named by `OBSERVER_SCHEMA` and grant the observer database role usage and table-creation rights there; this application will not create the schema itself. Configure every value from `.env.example` as a Vercel environment variable, including a randomly generated `CRON_SECRET` and a distinct `REPORT_READ_TOKEN`, each at least 32 UTF-8 bytes. Keep credentials outside source control. Independently verify and transfer the authority anchor pin; do not learn it from the source being observed. Generate an observer-owned ECDSA P-256 keypair with the pinned authority library and configure its canonical base64url PKCS#8 private key as `OBSERVER_SIGNING_PRIVATE_KEY` and SPKI public key as `OBSERVER_SIGNING_PUBLIC_KEY`. Transfer and pin the public key independently for report verifiers; a key reported only by this service cannot establish independent attribution. An authorized poll rejects an invalid or mismatched keypair before touching Postgres. The current source client expects a readable HTTPS governance feed; protected-source read authorization is pending a product decision. A local fixture is the only published feed today, so this is a deployable runtime, not a live 1bridge audit.

Generate the observer signing pair in a trusted local environment after `pnpm install`:

```sh
node --input-type=module -e 'import { generateSigningKey, exportSigningPrivateKey, exportSigningPublicKey } from "@drvillo/1bridge-authority"; const pair = await generateSigningKey(); console.log("OBSERVER_SIGNING_PRIVATE_KEY=" + await exportSigningPrivateKey(pair.privateKey)); console.log("OBSERVER_SIGNING_PUBLIC_KEY=" + await exportSigningPublicKey(pair.publicKey))'
```

Store the private value in the observer deployment secret store. Record the public value through the customer's trusted configuration channel. A report covers only the retained, replayed prefix and commits the unresolved finding set at its report revision. Staging-only cursor changes do not create new reports. Until an independent receipt archive is configured, it explicitly states `knownReceipts.kind = "none"`; it cannot attest that the provider exposed its latest action or every suppressed event. Finding resolution is not yet exposed by the store API; do not edit finding rows directly because that bypasses report revision tracking.

`reconcileRetainedReceipts(store, feedId, receipts)` is a programmatic comparison for up to 64 externally supplied integrated receipts at once. It replays one accepted database snapshot from the independently pinned anchor, then returns `matched` when the receipt's exact completion leaf and signed checkpoint belong to that chain, `pending` when the receipt's index or checkpoint is beyond the accepted prefix, or `unmatched` otherwise. Receipts for another feed are `unmatched`. Neither `pending` nor `unmatched` alone establishes provider wrongdoing: the supplied receipt may be forged or malformed, or the observer may still be catching up. This method neither stores the receipt nor changes a signed report. Independent receipt custody and an authenticated ingress are still required for a suppression-detection claim.

`vercel.json` invokes `GET /api/poll` once daily at 08:00 UTC, compatible with the Hobby cron interval. Vercel supplies `Authorization: Bearer <CRON_SECRET>` on its cron request. For manual catch-up, invoke the same route with that header from a trusted operator client; never put the secret in a URL or a browser page. Each call has a finite budget and returns `accepted`, `pending`, `up_to_date`, `busy`, `unavailable`, `source_nonconforming`, `quarantined`, or a configuration/poll error. Call again after `pending`; staged work and the lease epoch live in Postgres. The once-daily Hobby schedule and a 20-second work window limit catch-up speed, so an operator can make authorized manual calls for a backlog. Vercel does not automatically retry a failed cron invocation. Poll results are operational progress; signed coverage lives in the customer's `observer_reports` table. A separate read-only `GET /api/reports/latest` accepts `Authorization: Bearer <REPORT_READ_TOKEN>` and returns `{ "version": 1, "signedReport": ... }`, or 404 before any report exists. Both routes reject shared cron/read credentials before accessing Postgres. The read route needs the configured feed, independent anchor pin, database and observer public key; it remains available when polling-only source or cron configuration is invalid. `latest` means the highest stored signed report revision, which can lag the accepted cursor after a crash between acceptance and report publication until the next authorized poll recovers it. Consumers must inspect the signed checkpoint and time for their freshness policy; HTTP 200 alone does not establish current coverage. Give the read token only to intended consumers and verify the returned signature against the observer public key obtained through the customer's independent channel; the endpoint's configured key alone is not that trust anchor. Both routes return `Cache-Control: no-store` for authenticated responses.

`SOURCE_BASE_URL` must be an HTTPS origin with no credentials, path, query or fragment. Only `NODE_ENV=test` permits HTTP loopback fixtures. `FEED_ID` is 64 lowercase hex characters. `ANCHOR_PIN` is the 64-character lowercase hex output of the authority library's `anchorHash(anchor)`, obtained through an independently authenticated customer ceremony. `SIGNED_ANCHOR` is canonical unpadded base64url of UTF-8 `canonicalJson(signedAuthorityAnchor)`. A signed anchor may be fetched from the source, but it must verify against the independently configured pin; never derive or replace the pin from source responses. The async `verifyObserverAnchor` routine verifies the pin, both customer key-possession signatures and feed identity, then returns the initial authorized provider checkpoint public key and key ID from the verified anchor. The old `CHECKPOINT_PUBLIC_KEY` input is removed because the pinned anchor already authenticates that key. `DATABASE_URL` must identify a Postgres database. `OBSERVER_SCHEMA` selects an existing schema using a simple lowercase identifier; omit it for `public` in a dedicated database, or create a dedicated schema in a shared Postgres/Supabase project before installation. `CRON_SECRET` needs at least 32 UTF-8 bytes.

The first-party authority package is pinned to immutable commit `3a0ba58e94abdb529c60a8c02f63d3fce7df33db`. `pnpm-workspace.yaml` permits only that package's Git `prepare` build. A trusted operator must review upgrades before changing the commit and pin. The pull client treats a fetched target as provisional until the full signed history is replayed under the independently pinned anchor. The mixed HTTP fixture checks independently supplied completion receipts against the replayed chain; this is a verification contract only, because the observer does not yet retain external receipts. `test/governance-v1.json` is byte-for-byte identical to the authority package's fixed public vector; the observer serves it over the fixture HTTP source and verifies the exact target. The root `schema.sql` remains the frozen v1 migration; `schema-v2.sql` upgrades it and adds reports that the application only inserts. `schema-fingerprint.sql` checks an installed catalog before any idempotent DDL can conceal missing objects. The installer validates the old v1 catalog before upgrading, and validates the v2 catalog on later polls. `bash test/schema.sql.test.sh` still tests the v1 contract in a disposable `postgres:17` container; the runtime v1-to-v2 migration is covered by `pnpm test:integration`. To check DDL on a local Supabase Postgres container, set `OBSERVER_SUPABASE_CONTAINER` to its container name and run `bash test/schema.supabase.test.sh`. To check the runtime store against a local Supabase container, also supply a host-accessible `OBSERVER_SUPABASE_DATABASE_URL` and run `bash test/store.supabase.test.sh`. Both scripts create and remove a separate disposable database; they never install observer tables in the app database.

Run `pnpm test`, `pnpm test:integration`, `pnpm lint`, `pnpm typecheck`, `pnpm build`, and, with Docker available, `bash test/schema.sql.test.sh` to check this increment. `pnpm test:integration` starts and removes a disposable Postgres 17 container; the default `pnpm test` intentionally excludes real-database tests. [Architecture and implementation order](docs/architecture.md) describes the trust boundary, evidence ownership, planned verification path, and limits of source-only pulling.
