# 1Bridge independent observer

This public TypeScript/Next.js service independently **pulls** a signed pseudonymous governance registry and its advertised feed evidence from 1Bridge. It keeps accepted prefixes in observer-owned Postgres, replays authority and action signatures with [the authority library](https://github.com/drvillo/1bridge-authority), and signs aggregate reports distinguishing verified from pending feeds. It never gates a 1Bridge operation or release. A later published signed action citing a witnessed predecessor exposes a suppressed gap during catch-up. An event hidden from every independent witness and receipt holder cannot be inferred.

The shared deployment takes **no per-customer ID, token, source URL or feed list**. One third-party operator deploys it for all plans. Customer-operated Enterprise observers are a future deployment profile. The source must publish pseudonymous verification envelopes without private payloads. Configure `SOURCE_BASE_URL` for a deployed source with the public registry and feed routes before claiming coverage. Routine tests use a local synthetic source and independent Postgres; an opt-in contract can check a running 1Bridge Next source. Neither establishes deployed coverage.

## Deploy the shared profile

1. Install Node.js supported by Next.js 16 and pnpm 10.29.3. Run `pnpm install --frozen-lockfile`, `pnpm test`, `pnpm test:integration`, `pnpm lint`, `pnpm typecheck`, and `pnpm build`. Integration tests create and remove a disposable Postgres 17 container.
2. Create a Vercel project from this repository. Provision operator-owned Postgres, including Supabase Postgres if desired. A dedicated database can use `public`; for a shared database, create an observer-owned schema, grant its role `USAGE` and `CREATE` there, and set `OBSERVER_SCHEMA`. The service does not create the schema and does not need 1Bridge database credentials. Its v1–v4 migrations run transactionally and check the installed catalog fingerprint.
3. Independently obtain and pin the publisher's SPKI public key and **exact signed empty registry genesis**. Set `REGISTRY_PUBLISHER_PUBLIC_KEY` and `REGISTRY_SIGNED_GENESIS` from that trusted channel, not from the source being monitored. The library verifies the genesis signature and head chain against those pins.
4. Generate an observer-owned ECDSA P-256 pair in a trusted environment. Keep its PKCS#8 private key in Vercel secrets; distribute its SPKI public key to report verifiers through a separate trusted channel. Set `OBSERVER_SIGNING_PRIVATE_KEY`, `OBSERVER_SIGNING_PUBLIC_KEY`, `DATABASE_URL`, `SOURCE_BASE_URL`, and a random `CRON_SECRET` of at least 32 UTF-8 bytes. Use `.env.example` as the configuration checklist. Never commit secrets.
5. Deploy. `vercel.json` invokes `GET /api/shared-poll` once daily at 08:00 UTC with `Authorization: Bearer <CRON_SECRET>`. A trusted operator can call it again to catch up. Each call has a 45-second work budget, up to 12 registry entry/checkpoint pages and 12 round-robin feeds. Poll state, leases and accepted evidence survive function restarts in Postgres. An unavailable feed remains pending and does not stop its peers. Vercel does not retry failed cron runs automatically. Inspect report checkpoint and time for freshness; a once-daily Hobby schedule does not imply a maximum observation lag.

Generate a pair with the pinned library:

```sh
node --input-type=module -e 'import { generateSigningKey, exportSigningPrivateKey, exportSigningPublicKey } from "@drvillo/1bridge-authority"; const pair = await generateSigningKey(); console.log("OBSERVER_SIGNING_PRIVATE_KEY=" + await exportSigningPrivateKey(pair.privateKey)); console.log("OBSERVER_SIGNING_PUBLIC_KEY=" + await exportSigningPublicKey(pair.publicKey))'
```

The private key is printed to the terminal; run this only where its output can be handled securely. `SOURCE_BASE_URL` must be an HTTPS origin without credentials, path, query or fragment. HTTP loopback is allowed only in tests. Source endpoints and page limits are in [the shared observer contract](docs/shared-observer-plan.md). `GET /api/health` indicates process liveness only.

## Public verification interface

`GET /api/shared-reports/latest` returns `{ version: 1, reportHash, signedReport }` or 404 before the first report. `GET /api/shared-reports/status?reportHash=<64-lowercase-hex>&feedId=<64-lowercase-hex>` returns `{ version: 1, reportHash, proof }` for a feed in that report. Both are public, read-only, browser-readable from any origin (`Access-Control-Allow-Origin: *`), and `Cache-Control: no-store`; they expose pseudonymous feed IDs and cryptographic status, not customer identity or private payloads. Browser callers use noncredentialed GET requests. They require neither cron secret nor a customer-specific machine token.

A verifier must independently pin the observer public key, registry publisher public key, expected registry checkpoint and **its own feed ID and authority anchor pin**, then call `verifyAggregateFeedStatus` from the authority library. The proof or service cannot supply the expected customer identity. `verified` means the observer replayed the registry-advertised feed head; `pending` means it has not. HTTP 200 and the observer's own key configuration are not independent trust anchors. Reports retain the exact registry and verified replay snapshots needed to regenerate status proofs.

The database retains accepted and staged global registry entries/checkpoints, source findings, per-feed accepted evidence and signed reports. A transient registry source error is recorded; if a later accepted chain contains its target, the source-nonconformance finding is marked resolved while the record remains. An invalid replay remains a finding. A source outage is pending, not a tampering verdict. Registry checkpoints and signed action predecessor links make a later rewrite of a *witnessed* prefix detectable. The observer cannot prove that every action was published or that a never-witnessed tail existed.

The legacy `GET /api/poll` and token-protected `GET /api/reports/latest` routes remain for a separately configured single-feed installation; they are not the Vercel shared cron. The legacy profile uses `FEED_ID`, `ANCHOR_PIN`, `SIGNED_ANCHOR`, and `REPORT_READ_TOKEN`. It retains externally supplied completion receipts programmatically for independent comparison, but there is no public receipt-ingress route. Do not treat that archive as proof that all customers submitted receipts.

The authority dependency is pinned in `package.json` to a reviewed Git commit. `pnpm-workspace.yaml` permits only that dependency's Git `prepare` build. The v1–v3 migrations remain frozen; `schema-v4.sql` adds shared registry and aggregate tables. `bash test/schema.sql.test.sh` checks the v1 DDL in disposable Postgres. Fresh/v1/v2 upgrades and shared workflows are covered by `pnpm test:integration`, including a loopback HTTP source with two feeds, bounded catch-up, outage recovery and a missing-checkpoint finding. Optional Supabase scripts run against a separately supplied disposable Supabase Postgres database.

To check an actual 1Bridge source, start a disposable local app database and Next server with at least one published registry feed containing a signed leaf. Create the `observer_live_source` schema in a **separate disposable Postgres database**, then set `OBSERVER_TEST_DATABASE_URL`, `OBSERVER_LIVE_SOURCE_BASE_URL`, `OBSERVER_LIVE_REGISTRY_PUBLIC_KEY`, `OBSERVER_LIVE_REGISTRY_GENESIS`, `OBSERVER_LIVE_FEED_ID`, and `OBSERVER_LIVE_ANCHOR_PIN` from the independently retained test pins. Run `pnpm exec vitest run --config vitest.integration.config.ts test/live-source.integration.test.ts`. This opt-in test pulls the real public registry and feed routes, verifies the pinned signatures and signed leaf, persists the accepted head, and checks a signed aggregate coverage proof. It skips during the ordinary integration suite when those inputs are absent. Use only disposable test data; never point `OBSERVER_TEST_DATABASE_URL` at production.
