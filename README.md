# 1bridge independent observer

Public, customer-operated pull observer for 1bridge governance evidence. This repository has a bounded pull client, process-local fixed-target verification, a test-only HTTP governance source, a durable Postgres store, and a bounded poll route that resumes staged evidence after an outage. A malformed source response creates a durable nonconformance finding; an outage does not create a cryptographic accusation. The observer does not yet produce signed audit coverage or reconcile independently retained receipts. A running health endpoint is not an audit assurance.

## Run locally

Use Node.js compatible with Next.js 16 and pnpm 10.29.3. Run `pnpm install --frozen-lockfile`, then `pnpm dev` for the local app or `pnpm build && pnpm start` for a production build. `GET /api/health` returns `{ "status": "up" }` to indicate process liveness. The static home page states the current scope.

Copy `.env.example` to a private environment file and supply customer-controlled values. The configuration loader in `src/lib/config.ts` validates the runtime settings; the home page and health route do not read them. `src/lib/source.ts` fetches a provisional head and exact checkpoint/leaf pages; `src/lib/verify-source.ts` replays one fixed target under the independent anchor pin in a single process and refuses incomplete budgets. Tests exercise this path against a local HTTP governance publisher. `src/lib/store.ts` uses `pg` to install `schema.sql` inside one transaction, register exact independently pinned feed bytes, claim fenced database-time leases, fix one exact provisional target, and stage contiguous source bytes with an idempotent cursor. Staging advances no accepted coverage. `acceptObserverTarget` replays retained bytes under the independent pin before committing accepted rows; `quarantineObserverTarget` retains a complete rejected attempt and unresolved finding so corrected source bytes can be retried. `src/lib/poll.ts` bounds HTTP pages and elapsed time, resumes an active target after outage, and invokes acceptance or quarantine. The replay path is bounded to 10,000 leaves and 32 MiB. `openObserverStore(DATABASE_URL, schemaName)` requires the named schema to exist; it defaults to `public` in a dedicated observer database. The protected `GET /api/poll` route installs/checks the tables, claims a fenced lease, performs up to 16 leaf pages and 16 checkpoint pages within a 20-second work budget, and releases the lease. A signed coverage report is still pending, and the provider has no production governance feed yet, so no live independent coverage is claimed.

## Deploy on Vercel

Create a separate Vercel project from this public repository. Provision customer-controlled Postgres, either as a dedicated database or as a dedicated schema in a shared project. For a shared database, create the schema named by `OBSERVER_SCHEMA` and grant the observer database role usage and table-creation rights there; this application will not create the schema itself. Configure every value from `.env.example` as a Vercel environment variable, including a randomly generated `CRON_SECRET` of at least 32 UTF-8 bytes. Keep credentials outside source control. Independently verify and transfer the authority anchor pin; do not learn it from the source being observed. The current source client expects a readable HTTPS governance feed; protected-source read authorization is pending a product decision. A local fixture is the only published feed today, so this is a deployable runtime, not a live 1bridge audit.

`vercel.json` invokes `GET /api/poll` once daily at 08:00 UTC, compatible with the Hobby cron interval. Vercel supplies `Authorization: Bearer <CRON_SECRET>` on its cron request. For manual catch-up, invoke the same route with that header from a trusted operator client; never put the secret in a URL or a browser page. Each call has a finite budget and returns `accepted`, `pending`, `up_to_date`, `busy`, `unavailable`, `source_nonconforming`, `quarantined`, or a configuration/poll error. Call again after `pending`; staged work and the lease epoch live in Postgres. The once-daily Hobby schedule and a 20-second work window limit catch-up speed, so an operator can make authorized manual calls for a backlog. Vercel does not automatically retry a failed cron invocation. Poll results are operational progress only; accepted coverage is not yet a customer-signed audit statement.

`SOURCE_BASE_URL` must be an HTTPS origin with no credentials, path, query or fragment. Only `NODE_ENV=test` permits HTTP loopback fixtures. `FEED_ID` is 64 lowercase hex characters. `ANCHOR_PIN` is the 64-character lowercase hex output of the authority library's `anchorHash(anchor)`, obtained through an independently authenticated customer ceremony. `SIGNED_ANCHOR` is canonical unpadded base64url of UTF-8 `canonicalJson(signedAuthorityAnchor)`. A signed anchor may be fetched from the source, but it must verify against the independently configured pin; never derive or replace the pin from source responses. The async `verifyObserverAnchor` routine verifies the pin, both customer key-possession signatures and feed identity, then returns the initial authorized provider checkpoint public key and key ID from the verified anchor. The old `CHECKPOINT_PUBLIC_KEY` input is removed because the pinned anchor already authenticates that key. `DATABASE_URL` must identify a Postgres database. `OBSERVER_SCHEMA` selects an existing schema using a simple lowercase identifier; omit it for `public` in a dedicated database, or create a dedicated schema in a shared Postgres/Supabase project before installation. `CRON_SECRET` needs at least 32 UTF-8 bytes.

The first-party authority package is pinned to immutable commit `57c441f430ca1c4616167a0f97a67a2c273e087c`. `pnpm-workspace.yaml` permits only that package's Git `prepare` build. A trusted operator must review upgrades before changing the commit and pin. The pull client treats a fetched target as provisional until the full signed history is replayed under the independently pinned anchor. `test/governance-v1.json` is byte-for-byte identical to the authority package's fixed public vector; the observer serves it over the fixture HTTP source and verifies the exact target. The root `schema.sql` and `bash test/schema.sql.test.sh` define and test the observer-owned Postgres tables in a disposable `postgres:17` container. To check DDL on a local Supabase Postgres container, set `OBSERVER_SUPABASE_CONTAINER` to its container name and run `bash test/schema.supabase.test.sh`. To check the runtime store against a local Supabase container, also supply a host-accessible `OBSERVER_SUPABASE_DATABASE_URL` and run `bash test/store.supabase.test.sh`. Both scripts create and remove a separate disposable database; they never install observer tables in the app database.

Run `pnpm test`, `pnpm test:integration`, `pnpm lint`, `pnpm typecheck`, `pnpm build`, and, with Docker available, `bash test/schema.sql.test.sh` to check this increment. `pnpm test:integration` starts and removes a disposable Postgres 17 container; the default `pnpm test` intentionally excludes real-database tests. [Architecture and implementation order](docs/architecture.md) describes the trust boundary, evidence ownership, planned verification path, and limits of source-only pulling.
